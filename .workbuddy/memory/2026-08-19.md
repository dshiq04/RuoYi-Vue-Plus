## 修复：bigint→String 迁移导致的 PostgreSQL "character varying = bigint" 运行期错误（部门名称不显示）

用户列表 `/system/user/list?deptId=100` 部门名称不显示。日志 `logs/sys-error.log` 在 11:22:02 抓到：
```
org.postgresql.util.PSQLException: ERROR: operator does not exist: character varying = bigint
SQL: SELECT ... FROM sys_dept WHERE dept_id = ? AND del_flag = '0' AND tenant_id = '000000'
```
栈顶：`SysDeptServiceImpl.selectDeptById` → `BaseMapperPlus.selectVoById` → `selectById(id)`。

根因：实体主键 `Long → String` 迁移后，源码里 `SysDept.deptId` 已经是 `String`，**但正在运行的 JVM 仍加载迁移前的旧 class**（旧版 `SysDept.deptId` 是 `Long`），于是 MyBatis 按 `Long/bigint` 绑定参数，而 PostgreSQL 的 `sys_dept.dept_id` 已改为 `character varying`，PG 严格拒绝 `varchar = bigint`（MySQL 会隐式转换所以不报错）。
后果：`selectDeptById` 抛异常 → `DeptNameTranslationImpl.translation` 异常向上抛 → `TranslationHandler.serialize` catch 后回退写原始值 `gen.writeObject(value)`（即部门 ID "100"）→ 响应里 `deptName` 是 ID 不是名称 → 前端列表"部门名称不显示"（实际显示的是 ID）。

排查要点：
- 此类问题**编译期完全无感**，且只在严格类型数据库（PostgreSQL）上抛异常，MySQL 可能静默走隐式转换不报错（更隐蔽）。
- 翻译回退：`org.dromara.common.translation.core.handler.TranslationHandler#serialize` 的 catch 块会 `log.error("翻译处理异常…")` 并写原值；查 `sys-error.log` 关键字"翻译处理异常"或 PostgreSQL 的 "operator does not exist: character varying = bigint" 可定位。
- 翻译实现类的 Bean 注册：`ruoyi-common-translation/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 把 5 个 impl 列为自动配置 Bean（不是 `@Component`），`TranslationConfig.@PostConstruct` 收集 `List<TranslationInterface<?>>` 填入 `TRANSLATION_MAPPER`。所以翻译机制本身一直生效，不需要额外加 `@Component`（否则会与 common 模块循环依赖无关但语义重复）。

修复方案：**重启后端 Spring Boot 进程**，让 JVM 重新加载迁移后的 `target/` 类（`clean compile` 后产物已新鲜）。迁移后 `SysDept.deptId`/`parentId`/`leader` 等都是 `String`，与 PG 的 varchar 列匹配，绑定正常，`selectDeptById` 返回 `SysDeptVo.deptName`，翻译正常填充。
预防：迁移后除 `compile`/`test-compile` 通过外，必须**实际重启应用**并查日志确认无 PG `varchar=bigint` / MyBatis 类型绑定异常；MySQL 上同样的迁移可能不会报错但语义已错（隐式转换）。

全仓 `private Long` 实体字段复查：剩余均为数值列（`costTime`/`timeout`/`fileSize`/`accountCount`/`loginTime`），对应 SQL `bigint`，应保留 `Long`，无遗漏 ID 字段。
验证：`clean compile` BUILD SUCCESS、0 错误。

## 修复：SysDeptMapper.selectDeptAndChildById 非递归导致"部门名称不显示"

用户列表 `/system/user/list?deptId=100` 部门名称不显示。日志里该请求耗时仅 34ms（无过滤请求 127ms），强烈提示过滤命中行极少或为空。结合 JWT payload（admin `deptId="103"`、`deptName="若依集团"`），根因不在翻译，而在**过滤条件本身**：

`SysDeptMapper.selectDeptAndChildById(String parentId)` 原实现：
```java
List<SysDept> deptList = this.selectListByParentId(parentId);  // 只查一级子
List<String> deptIds = StreamUtils.toList(deptList, SysDept::getDeptId);
deptIds.add(parentId);
return deptIds;
```
方法名 "AndChild" 暗示递归取整棵子树，但实现**只取 parentId 的直接子部门 + 自身**，孙级及更深部门被遗漏。admin (103) 是 100 的孙级，过滤 `dept_id IN (直接子, 100)` 把 103 及后代用户全部排除，列表几近为空 → 前端看到没几行 → "部门名称不显示"（其实是无数据）。此 bug 与 `bigint→String` 迁移**无直接因果**，是迁移前后都存在的潜在问题，但迁移后用户集中测试才暴露。

修复：改为 Java 端递归 `collectChildDeptIds`，从 parentId 自身开始递归累加所有后代 deptId（用 `contains` 防环）。`selectListByParentId` 内部用 `DataBaseHelper.findInSet(parentId, "ancestors")`（`ancestors` 字段存祖先链如 `,0,1,2,`），所以子部门查询本身是匹配 ancestors 包含 parentId 的行——这意味着 `selectListByParentId(parentId)` 返回的恰好是 parentId 的**直接子**，递归调用即可覆盖全树。

`compile` BUILD SUCCESS、0 错误。需**重启后端**让新 `SysDeptMapper` 类生效，过滤 `deptId=100` 才能返回含 103 在内的完整子树用户，部门名称（通过翻译 `DeptNameTranslationImpl`）正常显示。

### 后续用户反馈："可以查出部门ID但是部门名称不显示"

递归修复后用户确认 **每一行能拿到 deptId，但 deptName 列显示的是 ID（如 100、103）而不是真实名称**。这是 `TranslationHandler.serialize` 的 catch 回退导致的：

```java
try {
    Object result = trans.translation(value, translation.other());
    gen.writeObject(result);
} catch (Exception e) {
    log.error("翻译处理异常，type: {}, value: {}", translation.type(), value, e);
    gen.writeObject(value);   // ← 回退：把 mapper 字段的原始值（deptId "100"）写到 deptName
}
```

即 `DeptNameTranslationImpl.translation` 调 `selectDeptById("100"/"103")` 时**抛异常**（旧 JVM 里 `SysDept.deptId` 还是 Long，被 PG 当 bigint 绑定到 varchar 列抛 `BadSqlGrammarException`），翻译 catch 后 `gen.writeObject(value)` 把原始 deptId 值写到 `deptName` 字段——前端看到的"部门名称"列其实就是 deptId。

判断标准：
- 部门名称列显示的是纯数字（deptId），不是真实名 → 翻译 catch 回退 → 重启加载 String `SysDept.deptId` 即可修复
- 部门名称列完全空白/null → 翻译根本没注册或返回 null，需检查 `TRANSLATION_MAPPER`（本项目走 `META-INF/spring/.../AutoConfiguration.imports`，已确认 5 个实现都在册）
- `sys-error.log` 应能看到 `翻译处理异常，type: dept_id_to_name, value: 100/103, ...` 与 PG `character varying = bigint` 堆栈

彻底修复仍依赖**重启后端**加载迁移后的 `SysDept.deptId=String`（递归 mapper 也需要重启加载，但递归本身不是 deptName 显示 ID 的根因，根因是 PG 类型绑定异常）。

### 三次踩坑：MySQL 的 CAST() 不支持 VARCHAR(n)

`/system/user/list` 报：
```
SQLSyntaxErrorException: You have an error in your SQL syntax ... near 'VARCHAR (2000)) AS path'
```
根因：**MySQL 的 `CAST(expr AS type)` 不支持 `VARCHAR(n)` 目标类型**（只支持 `CHAR(n)`、BINARY、DECIMAL 等）；PostgreSQL 支持 `VARCHAR(n)`。所以"同一份递归 CTE 兼容两库"不可行：
- `CAST('' AS VARCHAR(2000))`：PG ✓，MySQL ✗
- `CAST('' AS CHAR(2000))`：MySQL ✓（非 PAD_CHAR_TO_FULL_LENGTH 时读取自动去尾空格），PG ✗（bpchar 定长补空格，拼接会出现大量空格）

修复方案（项目未配置 MyBatis databaseIdProvider，故用 OGNL 静态方法调用区分）：
```xml
<choose>
    <when test="@org.dromara.common.mybatis.helper.DataBaseHelper@getDataBaseType().isMySql()">
        <![CDATA[ ... MySQL 版：CAST AS CHAR(2000) + CONCAT(dp.path,'/',d.dept_name) ... ]]>
    </when>
    <otherwise>
        <![CDATA[ ... PostgreSQL 版：CAST AS VARCHAR(2000) + dp.path || '/' || d.dept_name ... ]]>
    </otherwise>
</choose>
```
要点：
- MySQL 字符串拼接必须用 `CONCAT()`（`||` 在 MySQL 默认是 OR 运算符）；PG 用 `||`
- MyBatis OGNL 静态调用语法 `@全限定类名@静态方法().实例方法()`，`DataBaseHelper.getDataBaseType()` 返回 `DataBaseType` 枚举（有 `isMySql()`/`isPostgreSql()`）
- CDATA 内的 `${ew.customSqlSegment}` 仍会被 MyBatis TextSqlNode 替换（编译/启动已验证）
- MyBatis-Plus 分页 `PaginationInnerInterceptor` 对含 WITH 的 SQL 生成 COUNT 时保留 WITH 前缀、仅替换主 SELECT 为 `SELECT COUNT(*)`（CTE 未引用，MySQL 8/PG 均合法，优化器忽略）

### 四次踩坑：CTE + MyBatis-Plus 租户拦截器自动追加 tenant_id 条件

`/system/user/list` 报：
```
SQLSyntaxErrorException: Unknown column 'dp.tenant_id' in 'on clause'
SQL: WITH RECURSIVE dept_path AS (... parent_id IS NULL OR parent_id = '' UNION ALL
       SELECT ... FROM sys_dept d INNER JOIN dept_path dp ON d.parent_id = dp.dept_id
         AND d.tenant_id = '000000' AND dp.tenant_id = '000000' ...)
```

根因：**MyBatis-Plus 的 `TenantLineInnerInterceptor` 自动给所有目标表（包含递归 CTE）追加 `AND <alias>.tenant_id = '<当前租户>'`**。它把 `INNER JOIN dept_path dp ON ...` 视作 join，因此给 `d` 和 `dp` 都加 tenant 条件。但 `dept_path CTE` 锚点 SELECT 只选了 `dept_id/dept_name/parent_id`，**没有 `tenant_id` 列** → MySQL 报 `dp.tenant_id` 不存在。

修复：让 CTE 全链路把 `tenant_id` 列选出来，使 `dp.tenant_id` / `df.tenant_id` 真实存在，拦截器追加的条件才能合法：
- CTE 锚点：`SELECT dept_id, dept_name, parent_id, tenant_id, ...`
- CTE 递归：`SELECT d.dept_id, d.dept_name, d.parent_id, d.tenant_id, ...`
- `dept_final`：`SELECT dept_id, tenant_id, ... FROM dept_path`（让 `df.tenant_id` 也能被引用）

要点：
