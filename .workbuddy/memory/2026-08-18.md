## 在线令牌(ONLINE_TOKEN)按租户隔离的设计与修复

### 现象
后端加入"在线状态录入 Redis + 前端信息采集"后，登录接口本身成功（SSE 欢迎消息能发出），
但登录后所有需要鉴权的接口都返回 401，前端表现为"无法登录"。

### 根因
`JwtAuthenticationFilter` 新增在线令牌校验 `hasKey(ONLINE_TOKEN_KEY + token)` 返回 401。
该过滤器在**租户上下文之外**执行，而 `ONLINE_TOKEN_KEY` 写入时（登录在 `TenantHelper.dynamic` 内）
会被 `TenantKeyPrefixHandler` 自动加租户前缀；过滤器无租户上下文 → 不加前缀 → key 永远不一致 → 401。

### 最终方案：按租户ID查询 + 写入（用户明确要求租户隔离，不走 GLOBAL）
1. `CacheConstants.ONLINE_TOKEN_KEY` 改回普通键 `"ONLINE_TOKEN:"`（**不加** GLOBAL 前缀），
   与 `LOGIN_TOKEN_KEY`(GLOBAL) 区分，刻意保留租户隔离。
2. `ruoyi-common-security/pom.xml` 增加 `ruoyi-common-tenant` 依赖（tenant 不依赖 security，无循环依赖），
   使过滤器可用 `TenantHelper`。
3. `JwtAuthenticationFilter`：用已加载的 `loginUser.getTenantId()`，在
   `TenantHelper.dynamic(tenantId, () -> hasKey(ONLINE_TOKEN_KEY + token))` 内做在线令牌校验。
4. `SysLoginService.onLoginSuccess`：复用扫描 `getOnlineTokenByUserAndPlatform` 用
   `TenantHelper.dynamic(loginUser.getTenantId(), () -> ...)` 包裹，保证扫描也带租户前缀。

### 关键点 / 注意
- `RedisUtils.keys(pattern)` 返回的是**逻辑(已 unmap)键**；`getCacheObject(key)` 会在当前租户上下文重新 map。
  因此只要扫描与读取处于同一租户上下文即可正确往返（SysUserOnlineController / SysRoleServiceImpl 本就运行在
  登录用户租户上下文中，天然正确）。
- `TenantHelper.dynamic(tenantId, runnable/supplier)` 通过线程级 TEMP_DYNAMIC_TENANT 设置租户，
  即便 `LoginHelper.isLogin()` 为 false 也会设置线程级租户前缀，故过滤器中可用。
- `JwtUtils.invalidateToken` 删除 ONLINE_TOKEN 在各调用点(SaToken 已登录上下文)下均带正确租户前缀，无需改动。
- 旧键 `ONLINE_TOKENS:*` / `GLOBAL:ONLINE_TOKEN:*` 历史数据 7 天过期自动清理。
- `CacheNames.ONLINE_TOKEN = "ONLINE_TOKENS"` 是 Spring Cache 抽象名，与 redis key 无关，勿混淆。

## 多设备在线记录相互顶掉的修复（同一账号不同设备）

### 现象
安卓端登录后，PC 端原本的在线记录被"顶掉"（PC 记录被安卓登录覆盖/失效）。

### 根因
`onLoginSuccess` 中的"按平台(客户端+设备类型)复用令牌"逻辑（`getOnlineTokenByUserAndPlatform`）：
当安卓与 PC 解析到相同的 `clientKey`+`deviceType`（如共用同一个 OAuth2 client）时，安卓登录会复用 PC 的令牌，
并把**共享的**在线记录刷新成安卓的设备信息 → PC 的在线记录被顶掉；且同一令牌被两设备共用。

### 修复（移除复用，改回"每次登录独立令牌+独立在线记录"，即 commit e838336 的原始设计）
1. `SysLoginService.onLoginSuccess`：删除复用逻辑与 `getOnlineTokenByUserAndPlatform`，
   每次登录都生成独立 JWT 令牌并写入独立的 `ONLINE_TOKEN:<token>` 记录（仍在 `TenantHelper.dynamic` 内按租户隔离写入）。
   每个设备拥有自己的令牌与在线记录，互不覆盖 → 多设备正常录入/查询/校验。
2. `JwtUtils.invalidateToken`：**不能**放在 satoken 模块内按令牌租户精准删除——见下方"模块循环依赖修复"。
   现 revert 为简单的 `deleteObject(LOGIN_TOKEN_KEY+token)` + `deleteObject(ONLINE_TOKEN_KEY+token)`，
   依赖调用线程的租户上下文（普通登出请求由 TenantInterceptor 设置租户；同租户强退场景也正确）来拼接正确前缀。
3. `ruoyi-common-satoken/pom.xml`：**撤销**了 tenant 依赖（见下方循环修复）。
4. `SysUserOnlineController.forceLogoutToken`：批量强退时原先直接 `deleteObject(ONLINE_TOKEN_KEY+...)` 不带租户上下文，
   改为统一走 `jwtUtils.invalidateToken(...)`（同租户内正确删除）。

## 模块循环依赖修复（重要）

### 现象（用户编译报错）
`java: 模块循环不支持注解处理。请确保将循环 [ruoyi-common-satoken, ruoyi-common-tenant, ruoyi-common-mybatis] 中的所有模块排除在注解处理之外`

### 根因
新增的"多设备修复"中，给 `ruoyi-common-satoken` 加了 `ruoyi-common-tenant` 依赖，而既有依赖链为
`satoken ← mybatis ← tenant`（mybatis 依赖 satoken，tenant 依赖 mybatis），三者形成环：
`satoken → tenant → mybatis → satoken`。带注解处理(Lombok)的模块参与环会导致 Maven 编译报错。

### 修复（打破环）
- **撤销** `ruoyi-common-satoken/pom.xml` 中的 `ruoyi-common-tenant` 依赖。
- **撤销** `JwtUtils.invalidateToken` 对 `TenantHelper` 的引用（改回简单 deleteObject，依赖调用线程租户上下文）。
- `ruoyi-common-security` 的 tenant 依赖**保留**（security → tenant → mybatis → satoken 不构成环，security 不在环内）。

### 验证
`mvn -o -pl ruoyi-common/ruoyi-common-satoken,ruoyi-common/ruoyi-common-security,ruoyi-admin,ruoyi-modules/ruoyi-system -am compile -DskipTests`
→ BUILD SUCCESS（28 个模块全部 SUCCESS）。
- 注：本环境 Redis(6379)/MySQL(3306) 均未启动，无法在此完整 `run` 启动 Spring Boot；
  用户本地需先启动 Redis 与 MySQL 再 `mvn spring-boot:run`（或启动 ruoyi-admin）。

### 验证要点
- 用同一账号分别在 PC 与安卓登录：各自拿到不同令牌，在线用户列表(`/monitor/online`)显示该账号两条记录，
  互不影响；分别请求各自令牌均可正常通过 `JwtAuthenticationFilter` 校验。
- 安卓端登出/被强退：仅安卓令牌失效(401)，PC 端不受影响（之前会误删/误判）。
- 旧"复用"逻辑留下的历史在线记录 7 天自动过期。
- 已知权衡：同一设备重复登录会生成多个令牌（旧令牌 7 天内有效），属可接受范围；如需"同设备唯一会话"需另行引入稳定设备标识。
- 注：本环境 Git Bash 无法启动 Maven classworlds launcher，未能本地编译验证；代码为纯增量改动，请 `mvn` 重新构建后端并重启验证。

## MySQL(ruoyi_vue.sql) → PostgreSQL 转换

### 任务
将 `script/sql/ruoyi_vue.sql`(MySQL Navicat 全量导出，含 23 张表结构与 763 条数据) 转为 PostgreSQL，
输出到 `script/sql/postgres/postgres_ry_vue.sql`，风格对齐已有 `postgres_ry_vue_5.X.sql` 等文件。

### 转换规则（已实现于 `script/sql/postgres/_convert_mysql_to_pg.py`，可重跑）
- 小写 DDL；类型映射：bigint→int8, int→int4, tinyint(1)→int2, datetime→timestamp,
  char(1)→char, varchar→varchar, longblob→bytea, text→text。
- 注释外提为 `comment on table/column` 语句；主键为 `constraint "pk_<表>" primary key (...)`。
- 二级索引 `INDEX/UNIQUE INDEX ... USING BTREE (... ASC)` → `create [unique] index "<名>" on <表> (...)`。
- DML：去反引号；MySQL 二进制 `0xABCD` → PG bytea `'\xABCD'`；转义引号 `\'` → `''`；`NULL`→`null`。
- 丢弃 `SET NAMES/FOREIGN_KEY_CHECKS`、`/* Navicat */` 头、ENGINE/CHARSET/COLLATE/ROW_FORMAT、`default null`、原 `-- Table structure/Records` 横幅。

### 验证
输出 23 建表 / 763 插入 / 23 表注释 / 329 列注释；无反引号、无 MySQL 残留、无未转换 0x。
本机无 postgres，未实跑；语法符合 PG 规范，需用户在 PG 中 `psql -f` 验证。
